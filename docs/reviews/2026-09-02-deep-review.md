## Executive summary

**No committed secrets, credentials or personal data.** Every keyword hit in a repo-wide scan is a
fixture field key (`key: 'secret'`) or a hostile-URL test input (`file:///etc/passwd`); the only
email addresses in the tree are `a@b.co`, `a@b.com` and `someone@example.com`. Nothing needs
rotating. That was the first thing every slice looked for and it is clean.

There are **no CRITICALs**. Nothing here is remotely exploitable by an anonymous attacker against a
deployed formsmith, and the security posture of the two kits in particular is genuinely good — no
`dangerouslySetInnerHTML`, every `href`/`src` through `safeHref`, every document string narrowed
against a closed list before it reaches a `className` or an element type.

What the review found instead is one failure shape, reached from five different files, and it is the
thing to read this report for:

**When core cannot read something, it answers "hidden" — and hidden means unvalidated on the
server.** `validation.ts:586` states the correct rule in its own comment: *"A guard this code cannot
read has not said no, so the rule applies. The other direction skips the rule, which is a required
answer quietly becoming optional — on the server."* Four sibling call sites answer the other way.
`evaluateCondition` collapses UNREADABLE to `false` one line before `guardPasses` reads it, so a
malformed `when` silently disables a `required` rule. `runs` catches a host evaluator's throw and
returns `false`, hiding the node and its whole subtree — while the comment beside it claims
visibility "wraps the same call and says why". An unrecognised `op` hides. A `renderWhen` whose
`condition` is a truthy non-object hides. And the Binding panel's hint tells the author the opposite
of what happens. Each is defensible alone; together they are a class of document that validates
clean on a server and should not.

The other three findings that matter most all end the same way — the form is unsubmittable, or the
submit succeeds when it should not:

1. **`MissingType` renders no `children`** (`renderer/index.tsx:315`), so a document naming a
   component type the kit does not have discards its entire authored subtree while `validateForm`
   keeps validating every node inside it. A required field behind an unimplemented container is
   never drawn, never fillable, and blocks the submit with nothing on screen naming it — the exact
   outcome that function's own docblock says it exists to prevent.
2. **The Rules panel writes back a filtered rule list** (`Rules.tsx:172, 240, 242, 265`), so the
   first edit to any field silently deletes every rule the panel could not draw. Its docblock says
   "Dropped from the panel, never from the document." Opening the tab is harmless; editing is not.
3. **`applyChange` refuses to write into a row the renderer and `validateForm` both accept**
   (`rows.ts:583`). Three components in one package answer "what is a row that is not an object?"
   three different ways, and only the writer says "nothing" — so the field renders, reports
   "required", swallows every keystroke, and the submit can never be made to pass.

### Cross-cutting themes

Ordered by how much of the report each one explains.

**1. Unreadable input resolves toward "hidden", and hidden means unvalidated.** Described above.
`condition.ts:191`, `condition.ts:354`, `visibility.ts:54`, `visibility.ts:118`, `Binding.tsx:181`.
The fix is a single decision applied consistently, not five separate patches — and `validation.ts`
has already written down which way it should go.

**2. Guards that cannot fail, or that fail open.** The pattern recurs in the files whose whole
purpose is to fail. `count-reporter.ts:174` **disables its own suite-size check whenever a test file
stops being collected** — precisely the situation it exists to catch — by warning and returning with
no `exitCode`. `kit-contract.test.tsx:1064` drives a `Container` component neither kit ships, and the
`if (!has(...)) return` idiom means that row, and any other, passes green having asserted nothing.
`designer.css.test.ts` would lose the rule following any semicolon-terminated at-rule, and its parse
control asserts `> 20` blocks against a stylesheet with 158. `contrast.test.ts`'s document-table check
reduces over module state that a filtered run leaves empty. `readme.test.ts:190` is a loop with two
`continue`s and no control. `test/setup.ts` exports an observer counter nothing reads. `eslint.config.js`
enforces "no component library" with a five-name denylist that `@mantine/core` and `styled-components`
walk straight past.

**3. Fixtures that collapse the distinction under test.** The repository has a name for this — Trap 11
in its own `write-tests` skill — and it is the most common defect in the test slices. The depth
table asks `duplicateNode(root, 'root')` against a fixture rooted `box49999`, so the one genuinely
unbounded walker in `tree.ts` is never entered. `factory.test.ts`'s `__proto__` fixture is an object
initializer, which sets a prototype rather than creating the property the test is about.
`Designer.test.tsx` passes the same function identity while its own comment says "which is what an
inline arrow makes a new function on". `DocumentDialog.test.tsx` copies a draft it never edited.
`visibility.test.ts` tests row-over-form precedence with no key present in both scopes.

**4. Drag-and-drop is proven by nothing that can tell a drag from a click.** `e2e/harness.ts:225`
never waits for `.fs-drag-label`, and for a palette source with the target already selected, a
non-armed gesture produces a byte-identical document. Three specs rest on that. The drop indicator
`.fs-drop` is read by no browser test at all; tree drag-and-drop has no browser coverage; and jsdom
has no layout engine, so the unit tests are measuring zeros. This is the product's core interaction.

**5. Prototype-chain reads on document-supplied names.** The codebase has fixed this shape at least
four times with careful comments each time, and it survives in: `kit.renderers[node.type]`,
`resolveProps`'s accumulator, `store.setTranslation`/`setProp`, `json.ts`'s `record?.['label']`,
`css.ts`'s `css[name]`, `Icon.tsx`'s `GLYPHS[name]`, and `kit.ts`'s unvalidated `group`.

**6. Published compatibility promises nothing runs.** Every package declares React `^18 || ^19` and
installs only 19; `kit-mui` declares MUI `^6 || ^7` and installs only 7; all five declare
`engines.node >= 20` and CI runs only Node 22; and `pnpm e2e` resolves `@formsmith/*` to `src`, so
despite running last — after `build` and `check-dist` — no browser test has ever loaded a built
package. `designer` also requires a `react-dom` peer it never imports.

**7. Docblocks describing a fix the code does not implement.** This was the previous review's
headline and it recurs, though less often: `visibility.ts` claiming it made the choice it did not,
`Rules.tsx`'s "never from the document", `Properties.tsx`'s "are inverses", `Canvas.tsx`'s "nothing
edits the document mid-drag" (undo is not gated on a drag), and `StyleTab.tsx` using the announcement
pattern it condemns twelve lines earlier. Separately, **seven orphaned docblocks** now document the
function after the one they were written for — `tree.ts`, `context.ts`, `kit.ts`, `store.ts`,
`dnd.ts` (twice), `validation.ts` (twice) and `demo-server/index.ts`, where the file's most
